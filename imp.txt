some things to clarify or you can say you must understand ...


1. tcp is a stream, not message based
tcp doesnt preserver msg boundaries ... that is one write() on client != one read() on the server 
headers can arrive separated or split across reads ... or multiple req can arrive in one read
thats why ..
i accumulated data in buffer ... waited for CRLF CRLF (that is two \r\n) "\r\n\r\n" and parsed only after i detected a complete http header
this helps in understanding transport vs protocol framing


2. browsers normalize paths, attackers dont!
what browsers do yk .. they clean up the urls, collapse ../ and hide malicious intent 
but what attackers will do ... they will send raw tcp payloads and bypass browser behavior
thats why browser testing is misleading and i went with curl --path-as-is and netcat 
this helped me got one thing  ... that security decisions must be based on raw inputs and not browser behaviors


3. server side validation is a security boundary
clients cannot be trusted .. validation must happen after parsing and before routing ... 
if invalid input reaches routing then it is a bug 
my server rejects early traversal and never fixes malicious inputs and is not normalizing '..'
i mean this is nto feature, its just defensive programming


4. parsing, validation and normalization all three are different 
what are they lets understand
parsing means "is this syntactically correct?"
validation means "is this allowed?"
normalization means "what is the canonical form?"

so mixing them can causes bugs and issues so i kept them seperate 


5. memory safety came from bounded buffers + zero copy views 
i used fixed size buffers, explicit length tracking and struct string{data,len} instead of null terminated assumptions
there is no heap allocation, no strcpy, no unchecked pointer arithmetic

since i havent used heap allocation in request path, it gives me few benefits like
no leaks
no fragmentation etc etc
and a predictable behavior 

the entire request life cycle lives on stack

every read/write has a maximum size and checks remaining capacity and also fails safely if exceeded 
this prevents buffer overflow, memory corruption and remote crashes 

further more,
i am not assuming that paths are safe or headers are complete or strings are null terminated or even browsers behave correctly and things like that
everything is checked in the code

request life cycle in one para:
in my server a request is not treated as some high level object but simply as raw bytes coming from a tcp connection. 
after accept() i only get a connected socket, not an http request. tcp is stream based so one read() does not mean one 
full request, headers can come split across multiple reads. because of this i keep reading into a fixed size buffer and 
do not start parsing immediately. parsing only begins after i explicitly detect the http framing boundary which is 
CRLF CRLF (\r\n\r\n), since that marks the end of http headers. once the full header is present, i extract only the request 
line and parse it into method, uri and version based on spaces. parsing here only checks syntax, it does not decide whether 
the input is safe. after parsing i perform server side validation on the uri, this is the security boundary of the server. 
at this stage i reject any path that is invalid or attempts traversal like ".." before routing or filesystem access is even 
considered. browsers may normalize paths but attackers do not, so validation is done on raw input. optional path normalization 
can be applied only to already valid paths for consistency, but malicious input is never rewritten. routing is then done 
using simple string comparisons. the http response is constructed explicitly according to the protocol, including version, 
status code, reason phrase and content length. the response is written to the socket and the connection is closed using 
http/1.0 semantics. the entire request lifecycle uses bounded stack buffers, zero copy string views and no heap allocation, 
giving predictable memory usage, clear ownership and memory safety by design.
